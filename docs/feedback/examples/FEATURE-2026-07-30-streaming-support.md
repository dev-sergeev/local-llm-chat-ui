## Краткое описание

Если выбранный API поддерживает streaming, показывать ответ по мере получения реальных чанков. Для API без streaming сохранить текущий режим request-response без имитации потока.

## Пользовательский сценарий

1. Создать профиль провайдера с поддержкой streaming.
2. Отправить длинный запрос.
3. Увидеть первые токены до завершения всей генерации.
4. При необходимости нажать «Остановить».
5. После обновления страницы увидеть только корректно сохранённое состояние ответа.

## Фактический результат

Адаптер возвращает полный ответ после завершения внешнего вызова; UI показывает ожидание, затем весь текст.

## Ожидаемый результат

UI получает настоящие чанки, безопасно обновляет Markdown и сохраняет финальный ответ только после успешного завершения. Для неподдерживаемого API поведение остаётся прежним.

## Предлагаемое решение

Использовать существующую chunk-boundary абстракцию генерации и добавить streaming-реализации в адаптеры. Явно фиксировать capability профиля или определять её безопасным вызовом адаптера. Не смешивать транспортные чанки с транзакционным сохранением финального сообщения.

**Не входит в задачу:** имитация streaming, WebSocket между браузером и внешним провайдером и сохранение каждого токена в SQLite.

## Критерии готовности

- [ ] Первые реальные чанки отображаются до завершения генерации.
- [ ] Markdown остаётся безопасным при неполном блоке кода или таблице.
- [ ] Cancel немедленно прекращает обновление UI и запрещает позднее сохранение ответа.
- [ ] Retry не дублирует уже сохранённый финальный ответ.
- [ ] Ограничения на четыре генерации и четыре внешних вызова сохраняются.
- [ ] API без streaming автоматически используют request-response fallback.
- [ ] Поведение покрыто deterministic adapter-, HTTP- и frontend-тестами.
